# Data Model: Group Payment History

All storage is in memory inside the `Group` aggregate.

## Transaction (immutable record)

| Field | Type | Visibility | Rules |
|-------|------|------------|-------|
| `id` | String (UUID) | private | Generated by the system, unique per transaction, never serialized |
| `idempotencyKey` | String, nullable | private | Key the write was submitted with; `null` for legacy keyless calls; never serialized |
| `type` | `TransactionType` (`EXPENSE`, `SETTLEMENT`) | internal | Stored, not exposed |
| `payerId` | String (member uid) | public | Expense: the member who paid. Settlement: the member who sends money. Must be a group member |
| `receiverId` | String, nullable | internal | Settlements only |
| `amount` | BigDecimal | internal | Positive, scale at most 2 (existing rule); stored, not exposed |
| `description` | String | public | Trimmed, 1 to 200 characters; default `Expense` or `Settlement` when not provided |
| `recordedAt` | Instant (UTC) | public | Set by the server clock when the write is applied; never changed on replay |

## TransactionHistory (domain class, not thread-safe by itself)

- `List<Transaction> entries` in order of recording (append-only; no update or delete).
- Page cache: access-ordered map of page number to `TransactionPage`, max 100 entries.
- `append(Transaction)`: adds the entry and clears the page cache.
- `page(int page)`: `page >= 1` else `IllegalArgumentException`; returns the cached or newly built
  `TransactionPage`. The slice is taken from the end of `entries`, newest first, 10 per page.
- Invariants: one entry per applied balance change (FR-016); entries are never reordered; every
  `id` is unique.

## TransactionPage (immutable)

`items: List<Transaction>` (at most 10, newest first), `page: int`, `hasNext: boolean`.
A page beyond the last has empty `items` and `hasNext = false`.

## Group (changes)

- New fields: the `TransactionHistory` and a `Clock`.
- The existing key-to-fingerprint map is kept for idempotency; its fingerprint format is unchanged
  when no description is supplied.
- New: `getTransactionPage(int page)` (synchronized).
- Existing methods keep their signatures (see research R3).

## State and lifecycle

A transaction is created exactly once, at the moment the balance change is applied, and is then
immutable. Sequence for a key-taking write, all inside the group lock, in the SAME order the code
uses today so existing behavior is preserved:
1. normalize the description (needed to build the fingerprint; `null` means omitted, an invalid
   value throws `IllegalArgumentException` and nothing is recorded);
2. check for replay or conflict using the fingerprint (replay returns with no change; a different
   request under the same key is a `ConflictException`, even if that request would also be
   invalid, exactly as before);
3. validate member and amount (existing rules and messages);
4. apply balances;
5. record the key and append the transaction to the history (which clears the page cache).
A rejected or replayed request stops before step 5.

## Naming note

The existing code calls the Idempotency-Key `transactionId` in its method parameters. In this
feature the two are distinct: `Transaction.id` is a system-generated UUID, while `idempotencyKey`
is the client-supplied header value. New code MUST name the latter `idempotencyKey`.

## API view models (controller layer)

- `TransactionResponse { description, payerId, recordedAt }`
- `TransactionPageResponse { page, pageSize (10), hasNext, items: TransactionResponse[] }`
